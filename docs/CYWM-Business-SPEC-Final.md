# Бизнес-ТЗ: Автоматизация работы администратора с конфигурацией Wazuh v4.14.4

> **Статус:** Draft v0.1 · 2026-04-28
> **Целевая среда:** Wazuh **v4.14.4** + Laborato MDM + Windows-агенты
> **Объём:** Только автоматизация работы администратора с конфигурацией Wazuh v4.14.4. Vulnerability Management UI, Reporting, Incident Response, Threat Intelligence, Forensics — вне рамок этого документа.

---

## 1. Проблема

Администратор системы безопасности ежедневно вносит изменения в конфигурацию Wazuh: добавляет правила обнаружения, корректирует политики групп устройств, обновляет скрипты автоматического реагирования. Сегодня каждое такое изменение требует:

1. Подключения по SSH к серверу Wazuh
2. Ручного редактирования XML-файлов в `/var/ossec/etc/` через консольный редактор
3. Копирования `.cmd` / `.ps1` скриптов на Windows-устройства через RDP или общие сетевые папки
4. Ручной установки прав доступа на скопированные файлы (`icacls`)
5. Перезапуска службы `wazuh-manager` на Linux и `WazuhSvc` на Windows
6. Ручной проверки логов `/var/ossec/logs/ossec.log` на предмет ошибок

**Это создаёт следующие проблемы для бизнеса:**

| Проблема | Влияние |
|---|---|
| **Долгое внесение изменений** | 15-30 минут на каждую правку вместо 1-2 |
| **Высокий риск ошибки** | Опечатка в XML → Wazuh не запускается → SOC слепнет до восстановления |
| **Отсутствие аудит-следа** | Невозможно ответить "кто, когда, что менял" — провал на compliance-аудите |
| **Зависимость от одного человека** | Только опытный admin знает структуру файлов и команды, bus factor = 1 |
| **Отсутствие версионирования** | Невозможно посмотреть что было неделю назад и почему изменили |

---

## 2. Бизнес-цель

**Дать администратору возможность вносить любые изменения в конфигурацию Wazuh через единый веб-интерфейс внутри TRMM, без подключения к серверу или устройствам.**

Целевой результат: время одной правки сокращается **с 15-30 минут до 1-2 минут**. Риск выпустить нерабочую конфигурацию минимизируется за счёт автоматической проверки синтаксиса перед применением.

---

## 3. Целевые пользователи

| Роль | Что делает сейчас | Что будет делать |
|---|---|---|
| **Системный администратор** | Подключается по SSH к Wazuh, редактирует файлы, перезапускает службы вручную | Через UI редактирует и применяет конфигурации одной кнопкой |
| **SOC-аналитик** (после обучения) | Просит админа добавить правило | Сам создаёт и применяет правила без обращения к админу |
| **Аудитор** | Не имеет доступа к Wazuh | Просматривает историю всех изменений конфигурации |

> **Доступ к функциям.** В первой версии — все аутентифицированные пользователи TRMM имеют одинаковый полный доступ к функциям конфигурации Wazuh. Разделение по ролям (admin / read-only / approver) не реализуется. Все действия фиксируются в аудит-журнале с указанием конкретного пользователя.

## 4. Целевая среда

Система разрабатывается и тестируется под конкретную версию инфраструктуры:

| Компонент | Версия | Комментарий |
|---|---|---|
| **Wazuh manager** | **v4.14.4** | Используется новый формат `vulnerability-detection` (с 4.8+). Структура конфигурационных файлов и команды validation/restart соответствуют этой версии. |
| **Wazuh agent** (на Windows) | **v4.14.4** | Совпадает с manager. Path `C:\Program Files (x86)\ossec-agent\active-response\bin\` |
| **Laborato MDM** | Текущий установленный | Доработка ведётся в форке, фронт + бэк |
| **Windows endpoint** | Windows 11 / 10 / Server 2019+ | Целевая ОС для Active Response скриптов |
| **Linux (Wazuh server)** | Ubuntu 22.04 / любой поддерживаемый Wazuh | Доступ по SSH с паролем |

**Что это означает на практике:**

- Все шаблоны файлов в системе (правила, фрагменты ossec.conf, agent.conf) написаны под синтаксис **Wazuh v4.14.4**. При обновлении manager на новую мажорную версию шаблоны нужно проверить и при необходимости обновить.
- Команда проверки синтаксиса конфигурации — `/var/ossec/bin/wazuh-control configtest` (актуальна для 4.x).
- Команда перезапуска — `systemctl restart wazuh-manager` (актуальна для 4.x).
- Структура каталогов на сервере (`/var/ossec/etc/rules/`, `/var/ossec/etc/decoders/`, `/var/ossec/etc/shared/<group>/agent.conf`) — стандартная для Wazuh 4.x.

**Ограничение совместимости.** Если в будущем Wazuh изменит структуру конфигов или путь к утилитам (например, при выходе версии 5.x), система потребует доработки. Это явный технический долг, который должен отслеживаться при обновлениях Wazuh.

## 5. Что должна позволять делать система

### 5.1 Управление файлами конфигурации

Администратор должен через UI:

- **Просматривать** список всех конфигурационных файлов, разделённых по типу (правила, декодеры, фрагменты основного конфига, конфиги групп агентов, скрипты автоматического реагирования)
- **Создавать** новый файл выбрав тип и шаблон (готовые заготовки: пустое правило, фрагмент vulnerability-detection, шаблон Active Response скрипта и т.п.)
- **Загружать** существующий файл с локального компьютера
- **Редактировать** содержимое файла прямо в браузере с подсветкой синтаксиса
- **Удалять** файл (с возможностью восстановления в течение 30 дней)

**Поддерживаемые типы файлов:**

| Тип | Назначение | Где применяется |
|---|---|---|
| Правила (rules) | Кастомные правила обнаружения событий | Wazuh manager |
| Декодеры (decoders) | Парсинг кастомных форматов логов | Wazuh manager |
| Фрагменты ossec.conf | Настройка vulnerability-detection, Active Response команд | Wazuh manager (вставка в основной конфиг) |
| Конфиги групп (agent.conf) | Политики для группы устройств: какие сканы, как часто, что мониторить | Wazuh manager → разъезжаются на агентов автоматически |
| Скрипты Active Response | `.cmd` / `.ps1` для автоматического реагирования | Windows-агенты |

### 5.2 Импорт существующих конфигураций

При первом подключении системы к существующему Wazuh manager администратор может одной кнопкой импортировать в систему все уже существующие файлы конфигурации, чтобы не вводить их заново.

### 5.3 Применение изменений на сервере (деплой на Wazuh manager)

Одной кнопкой "Применить" система должна:

1. Запустить **автоматическую проверку синтаксиса** новой конфигурации (через встроенный валидатор Wazuh)
2. Если синтаксис некорректен — **не применять изменение**, оставить рабочий конфиг на сервере нетронутым, показать администратору конкретное место и описание ошибки
3. Если синтаксис корректен — сделать резервную копию текущей версии файла на сервере (для возможности ручного восстановления при необходимости)
4. Загрузить новую версию файла в правильное место на Wazuh manager
5. Установить корректные права доступа
6. Перезапустить службу `wazuh-manager` (если требуется для типа файла)
7. Показать администратору полный лог операции

Для конфигов групп агентов (`agent.conf`) перезапуск не выполняется — Wazuh синхронизирует их автоматически.

### 5.4 Применение изменений на устройстве (деплой на Windows-агент)

Одной кнопкой "Применить" система должна:

1. Передать файл (Active Response скрипт) на выбранное Windows-устройство
2. Установить корректные права доступа (чтобы скрипт мог запускаться от системы)
3. Опционально перезапустить службу Wazuh на устройстве
4. Показать результат операции

### 5.5 Использование переменных в файлах

В содержимом любого файла можно использовать заменяемые шаблоны (например, `<WAZUH_SERVER_IP>`, `<TRMM_SERVER_IP>`). Значения задаются один раз в настройках системы и подставляются автоматически при применении.

**Зачем:** один и тот же скрипт можно использовать в разных окружениях без правки.

### 5.6 Управление сервисами

Через UI администратор может:

- **Перезапускать** службу `wazuh-manager` на сервере
- **Перезапускать** службу Wazuh-агента на любом Windows-устройстве
- **Видеть статус** служб (работает / остановлена / ошибка)

### 5.7 Просмотр логов Wazuh manager

Администратор может через UI:

- Видеть последние 100 строк лога Wazuh manager
- Включить **режим живого просмотра** — лог обновляется автоматически каждые несколько секунд
- Использовать это для отладки только что применённых изменений (увидеть как Wazuh подгружает новое правило в реальном времени)

### 5.8 История изменений

Система должна хранить:

- **Историю редактирования** каждого файла — все версии содержимого с указанием кто и когда менял
- **Историю применений** — все деплои на сервер/устройства с полным логом операции (успех/ошибка, что именно произошло)

Администратор может просмотреть любую предыдущую версию файла и при желании скопировать её содержимое в текущий редактор для повторного использования.

> **Откат как отдельная функция в этой версии не реализуется.** Если администратору нужно вернуть предыдущую версию — он находит её в истории, копирует содержимое в редактор и применяет как новое изменение. Это создаёт явный аудит-след "кто и когда вернул старую версию".

### 5.9 Аудит действий

Каждое действие пользователя в системе должно записываться в журнал:

- Кто (имя пользователя)
- Когда (точное время)
- Что (создание/редактирование/удаление файла, деплой, перезапуск)
- Объект действия (имя файла, имя устройства)
- Результат (успех / ошибка с описанием)

Журнал должен быть доступен для просмотра в UI и выгрузки в CSV.

### 5.10 Подключение к Wazuh manager

Один раз администратор настраивает подключение системы к Wazuh manager:

- Адрес сервера и порт
- Имя пользователя для SSH
- Пароль или приватный ключ

Введённые секреты должны храниться зашифрованными.

Кнопка "Проверить подключение" сразу проверяет работоспособность настроек.

## 7. Критерии приёмки

Внедрение считается успешным, если выполнены **все** условия:

1. **Полный цикл работы без SSH/RDP.** Администратор от начала до конца — создаёт правило, применяет на manager, создаёт скрипт реагирования, применяет на Windows-устройство, проверяет работу через логи — без единого подключения к серверу или устройству.

2. **Автоматическая защита от ошибок.** Сознательно введённый невалидный XML в правиле — система не применяет его на сервер, выдаёт описание ошибки, рабочая конфигурация остаётся нетронутой.

3. **Аудит за период.** За любой период (день / неделя / месяц) можно получить полный список изменений конфигурации с указанием user/time/action/target.

4. **История версий.** Для любого файла можно посмотреть содержимое любой из предыдущих версий и кто её сохранил.

5. **Время правки.** Контрольное измерение: добавление одного нового правила обнаружения и применение его на manager занимает менее 2 минут.

6. **Передача знаний.** Сотрудник, не имеющий опыта работы с консолью Wazuh, после 30-минутного обучения самостоятельно вносит изменение и применяет его.

## 8. Что НЕ входит в задачу

Чтобы избежать недоразумений:

- **Просмотр уязвимостей, генерация отчётов, управление инцидентами, threat intelligence, forensics** — вне рамок. Эти функции вынесены в отдельные ТЗ.
- **Замена дашборда Wazuh** — мы автоматизируем работу с **конфигурациями**, а не строим заново мониторинг и аналитику.
- **Управление Linux-агентами** — в первой версии только Windows-агенты (через TRMM).
- **Поддержка нескольких Wazuh-серверов одновременно** — в первой версии один Wazuh manager на инсталляцию.
- **Графический редактор правил** (drag-and-drop) — администратор работает с XML напрямую, как это уже умеет.
- **Удаление данных с устройства** — функция целенаправленно исключена.
- **Автоматический откат на предыдущую версию** — в первой версии не реализуется. Восстановление через копирование содержимого нужной версии из истории и применение как нового изменения.
- **Разделение прав по ролям (RBAC)** — в первой версии все аутентифицированные пользователи TRMM имеют одинаковый доступ. Контроль через аудит-журнал. RBAC будет добавлен в одной из следующих версий.

## 10. Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Администраторы продолжат пользоваться SSH несмотря на UI | Средняя | Высокое | Закрыть прямой SSH к Wazuh для всех кроме одного человека |
| Уязвимость в системе даёт привилегированный доступ к Wazuh | Низкая | Критичное | Все секреты зашифрованы, обязательная авторизация TRMM, аудит, pentest перед production |
| Ошибочное изменение применилось и сломало работу Wazuh (отката нет) | Средняя | Среднее | Автоматическая проверка синтаксиса блокирует применение; история версий позволяет вручную скопировать предыдущее содержимое и применить как новое |
| Любой пользователь TRMM может применить изменение в Wazuh (нет ролей) | Средняя | Среднее | Все действия фиксируются в аудите; ограничить круг учётных записей TRMM, имеющих доступ к системе; в следующих версиях добавить RBAC |
| Производительность UI деградирует при сотнях файлов | Низкая | Низкое | Пагинация, индексы в БД, тестирование на демо-окружении |
| Несовместимость с будущим обновлением TRMM | Средняя | Среднее | Минимальное вторжение в код TRMM, подписка на их changelog |
